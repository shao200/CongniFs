# ADR-0004 · 单一响应式前端

- 状态：已采纳
- 日期：2026-11-26
- 决策者：作者
- 关联：`03 §9.1`、`02 §1.3`、`11 §6`

## 背景

D3 已决定双端并行（PC + 手机）。单人开发下，若两端各写一套前端，业务逻辑必然漂移，R13 会立刻发生。

## 问题

如何在「两端同时可用」的前提下，把实现成本与漂移风险压到最低？

## 选项

### A. 一套响应式前端 + 两套布局

同一代码库，按断点切换桌面/移动布局，能力差异用功能开关控制。

- 优点：业务逻辑只有一份；组件复用；测试可共用；增量最快。
- 缺点：移动端需要接受桌面组件的裁剪；响应式细节多；PWA 限制需统一处理。

### B. 两套独立前端

PC 用 React，手机单独一套（甚至不同框架）。

- 优点：各自体验最优。
- 缺点：两份逻辑、两套测试、两倍缺陷；单人不可维护。

### C. 共享组件库 + 两套壳

组件复用，但路由与状态各自实现。

- 优点：比 B 轻。
- 缺点：状态与请求逻辑仍会分叉，问题只是被推迟。

## 决策

采用 **A：一套响应式前端**，PC 与手机共用同一套页面与状态层，仅布局与能力分档不同。

## 理由

1. 双端并行的真正瓶颈是人，不是设备；一份实现才可能同时推进。
2. 01 已经把手机定义为「捕捉 + 对话 + 只读档案」，裁剪是设计的一部分，不是妥协。
3. 契约与 SDK 共用后，两端行为天然一致，评测与缺陷修复只需做一次。

## 后果

### 正面

- 新增功能默认双端同时获得（除非显式分档）。
- E2E 可用同一套用例跑两个 viewport。
- 视觉与交互规范只需维护一套。

### 负面 / 代价

- 移动端交互复杂度受限，不能为手机做完全不同的信息架构。
- 响应式与触控适配需要额外测试。
- PWA 的安装、离线、证书限制必须在前端统一处理。

### 必须配套的约束

- 能力分档必须用**能力开关**实现，不允许 `if (isMobile) { 另一套业务逻辑 }`。
- 所有数据访问走同一 SDK，禁止移动端私写请求。
- 断点与布局规则集中在 `layouts/`，页面不感知设备类型。
- 移动端不提供修正/遗忘等写操作（D8），只做只读引导。

## 复审条件

- 若手机端出现无法用响应式满足的核心交互（例如重度离线编辑）→ 评估原生壳，但仍复用同一 API。
- 若响应式导致 PC 端体验明显退化 → 允许在布局层分叉，不允许在业务层分叉。
- 若双端测试成本超过收益 → 优先削减手机功能，而不是拆代码库。
