# ADR-0005 · SQLite + sqlite-vec 单库

- 状态：**待验证**（方案已选定，加密组合待 spike 结论）
- 日期：2026-11-26
- 决策者：作者
- 关联：`03 §9`、`04 §5`、`06 §3`、`09 §15`

## 背景

系统需要同时承担：事件账本、记忆关系、全文检索、向量检索、审计记录。单用户、本地优先、零运维是硬约束。加密方案（SQLCipher）与 `sqlite-vec` 的兼容性尚未验证。

## 问题

用什么存储组合，能在最小运维成本下同时满足事务、全文、向量与加密？

## 选项

### A. SQLite + FTS5 + sqlite-vec（单文件）

- 优点：单文件、零运维、备份即拷贝；事件与向量同事务；审计与检索同库。
- 缺点：向量规模有上限；SQLCipher 兼容性未知；单写者模型。

### B. SQLite + 独立向量库（LanceDB / Chroma）

- 优点：向量能力强，规模更大。
- 缺点：两套存储、两套备份、两套一致性；`local_only` 内容可能落在未加密的向量文件里。

### C. Postgres + pgvector

- 优点：成熟、并发好、SQL 能力强。
- 缺点：需要常驻服务；对单用户本地应用是运维负担；备份与分发复杂。

## 决策

采用 **A：SQLite（WAL）+ FTS5 + sqlite-vec 单库**。

加密采用两级策略：

1. `event_payloads` **始终**做字段级 AES-GCM 加密（与存储选型无关）。
2. 全库加密优先尝试 SQLCipher；若与 `sqlite-vec` 不兼容，则退回「字段级加密 + 依赖操作系统整盘加密」。

最终加密结论以第一周 spike 为准，并回写本 ADR。

## 理由

1. 单用户场景下，运维成本比理论扩展性重要得多。
2. 审计要求「记忆与证据同库同事务」，独立向量库会破坏这一点。
3. 向量是可重建的派生数据，规模上限可以通过分区/降维解决，不值得为它引入第二套存储。
4. 备份即拷贝，灾难恢复路径最短。

## 后果

### 正面

- 一套迁移、一套备份、一套一致性校验。
- 遗忘可以在一个事务内同时清理正文、向量、FTS 与边。
- 本地部署无额外依赖。

### 负面 / 代价

- 向量超过约 100 万条后，暴力检索会变慢，需要 IVF 分区或降维。
- 单写者模型：长事务会阻塞写入。
- 若 SQLCipher 不可用，加密强度依赖操作系统整盘加密。

### 必须配套的约束

- 向量表必须可重建，禁止把它当作唯一真相。
- 检索前做存在性校验，避免索引滞后返回已删除内容。
- 所有写入使用短事务；批量索引用独立作业。
- 备份必须包含 `-wal` 状态或先 checkpoint。

## 验证计划（第一周 spike）

| 项 | 方法 | 通过标准 |
|---|---|---|
| SQLCipher × sqlite-vec | 最小程序：建库、写 1 万向量、查询、重开 | 无崩溃，结果正确 |
| 加密后性能 | 10 万行读写 | 退化 ≤30% |
| FTS5 trigram 中文 | 20 条查询 | 召回满足 07 §10 |
| 磁盘占用 | 1 万记忆 + 向量 | 估算可接受 |

## 复审条件

- spike 失败 → 切换到「字段级加密 + 整盘加密」，并更新本 ADR。
- 向量规模持续超过 100 万 → 评估 IVF / 降维 / 外置向量库，但必须解决加密与一致性。
- 出现多端并发写同一库的需求 → 该需求本身与架构冲突，应通过事件同步解决，而非换数据库。
