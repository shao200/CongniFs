# ADR-0006 · 进程内任务队列

- 状态：已采纳
- 日期：2026-11-26
- 决策者：作者
- 关联：`03 §1/§4.4`、`09 §5`、`08 §3`

## 背景

系统有大量异步工作：嵌入、打标、摘要、张力扫描、遗忘级联、保真度抽样。它们不能阻塞对话主链路，但也不需要跨机器分发。

## 问题

用什么机制执行后台任务，才能既可靠又可观测，且不引入额外运维？

## 选项

### A. SQLite `jobs` 表 + 进程内 worker

- 优点：零中间件；任务可查、可重放、可人工重试；与主库同事务投递。
- 缺点：不能水平扩展；并发受单进程限制；长任务会占用进程资源。

### B. Redis + BullMQ

- 优点：成熟的队列语义、并发与重试。
- 缺点：多一个常驻服务；本地部署与备份复杂；单用户场景收益极低。

### C. 操作系统定时任务 / 独立 worker 进程 + 文件锁

- 优点：进程隔离。
- 缺点：调度与重试要自己实现，跨平台差异大。

## 决策

采用 **A：SQLite 作业表 + 进程内 worker**，预留 `--worker-only` 启动参数用于将来拆分。

## 理由

1. 单用户本地应用，任务量以「每天数百」计，不需要分布式队列。
2. 作业与事件同库，可以在同一事务里「写事件 + 投递任务」，避免丢任务。
3. 作业状态可见即可运维：失败、死信、重试都能在设置页展示。

## 后果

### 正面

- 没有额外进程与服务，安装即用。
- 作业天然可审计、可重放。
- 备份数据库即备份了任务状态。

### 负面 / 代价

- 无法水平扩展。
- 进程崩溃时，运行中的作业需要靠锁超时回收。
- 重任务（如批量摘要）可能影响 API 延迟。

### 必须配套的约束

- 领取任务使用单条 `UPDATE ... RETURNING`，避免竞态。
- `UNIQUE(kind, idempotency_key)` 保证重复投递不重复执行。
- 启动时把 `running` 且锁定超时的作业重置为 `queued`。
- 每类作业有独立并发上限；摘要不得挤占嵌入。
- 死信必须可见，且可手动重放。
- 当 API P95 受 worker 影响时，先拆进程（`--worker-only`），不换队列。

## 复审条件

- API 延迟因 worker 明显退化 → 拆分独立 worker 进程（同一份代码）。
- 出现多设备同时执行后台任务的需求 → 通过事件同步协调，不引入分布式队列。
- 任务量增长到单进程无法消化 → 先优化批处理与并发，再评估外部队列。
