# ADR-0002 · 双时态记忆

- 状态：已采纳
- 日期：2026-11-26
- 决策者：作者
- 关联：`00 §5.2`、`04 §3`、`05 §7`

## 背景

产品承诺能回答「我三个月前怎么看这件事」。原始设计只用 `created_at` + `version` 号保留历史。但「系统何时记下」与「你何时这么想」是两件事：一次补录、一次修正，都会让单时间轴失真。

## 问题

如何在不引入复杂度的前提下，既能还原任一时点的认知，又能保留修正历史？

## 选项

### A. 单时间戳 + 版本号

只记录创建时间与版本计数。

- 优点：简单。
- 缺点：无法区分「当时这么想」与「当时才记下」；修正后无法还原旧认知。

### B. 只加版本链

保留每次修正的内容，按版本回溯。

- 优点：能看单条演化。
- 缺点：无法回答「某个时间点，系统整体认为什么」；跨条目的快照不可得。

### C. 双时态

同时记录 `valid_from/to`（认知有效期）与 `tx_from/to`（记录有效期）。

- 优点：支持单条回溯、全局快照、演化对比。
- 缺点：每个查询都必须明确时间轴；误用会导致静默错误。

## 决策

采用 **C：双时态**，并规定所有查询必须显式声明时间轴。

## 理由

1. 「过去的你」是核心差异功能，不能靠近似实现。
2. 修正必须「关闭旧版本 + 插入新版本」，双时态让这件事自然成立。
3. 误用风险可以通过「只允许调用统一查询函数」来控制，而不是靠放弃能力。

## 后果

### 正面

- 支持 `current()`、`as_of(T)`、`evolution()`、`history()` 四类查询。
- 修正不破坏历史，满足 A5（可逆）与 A4（可审计）。
- 冲突判定可以基于 `valid_time` 是否重叠，避免把「演化」误判为「矛盾」。

### 负面 / 代价

- 查询复杂度上升，索引与字段更多。
- 开发者容易把 `created_at` 当 `tx_from`，或用 `updated_at` 当 `valid_to`。
- 界面必须区分「历史版本」与「当前判断」。

### 必须配套的约束

- 修正只允许「关闭旧行 + 插入新行」，禁止原地更新内容。
- 所有时间相关查询必须走 `v_memory_current` / `as_of()` / `history()` 三个入口。
- 禁止在业务代码中手写 `tx_from <= ?` 的散装条件。
- 不在 `as_of` 结果中混入已遗忘且内容为空的行。

## 复审条件

- 若 P1 结束后「过去卡片」使用率长期为零 → 评估是否降级为按需查询，但**不删除已写入的时态字段**。
- 若查询性能成为瓶颈 → 先加索引与物化，不改变语义。
