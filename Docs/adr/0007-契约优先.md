# ADR-0007 · 契约优先

- 状态：已采纳
- 日期：2026-11-26
- 决策者：作者
- 关联：`03 §5`、`09 §1/§10`、`11 §5.2`

## 背景

D3 要求双端并行。若两端各自定义请求/响应结构，字段名、可空性、错误语义都会漂移；而单人开发没有余力维护两套 DTO 与两份文档。

## 问题

如何保证 PC 与手机、前端与后端在长期演进中不产生结构漂移？

## 选项

### A. Zod 单一真相 → OpenAPI → 生成客户端

schema 只写一次，生成 OpenAPI 文档与类型化 SDK，两端只用 SDK 调用。

- 优点：类型与运行时校验一致；漂移在 CI 就被发现；文档自动同步。
- 缺点：多一步代码生成；schema 演进需要纪律；生成代码不可手改。

### B. 各端手写 DTO

后端定义一套，前端再写一套。

- 优点：无工具链成本。
- 缺点：必然漂移；错误语义不一致；评审成本高。

### C. GraphQL schema

以 GraphQL 作为契约。

- 优点：查询灵活、强类型。
- 缺点：为本地简单 API 引入不必要复杂度；SSE 与文件流处理更麻烦；缓存与鉴权模型不匹配。

## 决策

采用 **A：契约优先**。`packages/contracts` 是唯一真相，生成 OpenAPI 与类型化客户端。

## 理由

1. 双端并行的前提是接口先冻结，而不是「先各写各的」。
2. Zod 同时给出静态类型与运行时校验，适合本地 API 的 fail-closed 要求。
3. 生成 SDK 让「手机端私扩字段」在类型层面就不可能发生。

## 后果

### 正面

- 双端行为一致，缺陷只修一次。
- 错误码、分页、幂等键在契约层统一。
- 契约变更可被 CI 审查与归档。

### 负面 / 代价

- 需要维护代码生成流程。
- schema 变更必须走评审，不能随手改。
- 生成产物需要纳入版本控制或构建缓存策略。

### 必须配套的约束

- P0 第一周冻结四组 API（对话/检索/审计/遗忘）。
- 冻结后只增不改；破坏性变更升级到 `/v2`。
- CI 校验 schema diff，出现 breaking 必须显式批准。
- 生成代码禁止手改，修改只能回到 schema。
- 所有错误必须使用统一封装与预定义错误码（03 §5.3）。

## 复审条件

- 若生成链路成为开发瓶颈 → 可替换生成工具（如 ts-rest / openapi-typescript），但**不得放弃单一真相**。
- 若出现无法用 REST 表达的核心能力（例如复杂订阅）→ 先评估 SSE 扩展，再考虑协议变更。
- 若契约冻结导致 P0 无法推进 → 缩小冻结范围到四组核心端点，不取消冻结。
