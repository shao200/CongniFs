## 0. 三条链，一份协议

```
写入链：事件 → 投影 → 候选 → 确认 → active → 可注入
使用链：语境 → 候选 → 过滤 → 打分 → 裁剪 → 注入 → 回执
遗忘链：预览 → 确认 → 七步级联 → 墓碑 → 回执 → 全局隐藏
```

三条链共享一个原则：**任何一步不满足条件，该条记忆就不进入下一步**（fail-closed）。本文所有「不通过」的分支都写明了用户会看到什么，不允许静默处理。

### 0.5 与私有知识库的关系（v0.4）

- **记忆是知识库的子集**：知识库分「世界知识」（文档、分块、实体、事实、关系）与「用户知识」（偏好、判断、承诺、对话情景）。
- 本文只管**用户知识**的写入、注入、保真与遗忘；世界知识的接入、解析、分块与整理见 `14`。
- 对话注入时两路并取：世界知识给事实与原文，用户知识给你此前的判断与偏好；两者分开标注，不混为「我记得」。
- 证据、双时态、隐私标签、遗忘级联两套共用。

## 1. 写入协议

### 1.1 五类入口

| 入口 | 事件 `origin/kind` | 是否直接产生记忆 | 说明 |
|---|---|---|---|
| 用户显式要求记住 | `capture/note` + `explicit_remember` | 是 | `origin=user_explicit`，可立即 `active` |
| 用户表达判断 | `conversation/judgment` | 否 | 进摘要与候选队列，需确认 |
| 系统抽取 | `system/tag` / `summary` | 否 | `origin=system_inferred`，最高只能到 `proposed` |
| 修正 | `*/correction` | 是 | 生成新版本，关闭旧版本 |
| 遗忘 | `*/forget` | — | 触发级联 |

### 1.2 投影规则

| 事件 kind | → 记忆 type | 默认层 | 条件 |
|---|---|---|---|
| `judgment` | judgment | L2（高置信 + 已确认 → L1） | 必须有 evidence |
| `commitment` | commitment | L1 | 必须有 `valid_to`（截止时间） |
| `preference` | preference | L3 | 压缩为常量，不逐条注入 |
| `fact` | fact | L1 | 必须 `user_confirmed` 或 `user_explicit` |
| `note` | event 或 relation | L2 | 需要打标后才能判定 |
| `utterance` | 不产生记忆 | — | 只参与摘要 |

**写入禁止项**（对应 I10）：

- 系统不得把自己生成的内容写成 `user_judgments`。
- 系统不得在无 evidence 的情况下创建 `active` 记忆。
- 系统不得把「用户否定过的建议」重新包装成用户偏好。

### 1.3 确认制

```
system_inferred ──► proposed ──用户确认──► active
                     │
                     ├──用户修正──► corrected（同时生成 active 新版本）
                     └──30 天未处理──► 丢弃（不落库）
```

确认入口只有一个：`POST /v1/candidates/:id/{confirm|edit|ignore}`。P0 只处理会话结束后的候选队列（每场上限 5 条）；P1 扩展到捕捉内容。

**去重**：同一 `content_hash + subject + valid_from` 在 24 小时内只允许一条 `active`，重复写入转 `superseded`。

### 1.4 记忆类型规则

| 类型 | 半衰期 | 有效期 | 需要 evidence | 可被谁覆盖 | 过期行为 |
|---|---|---|---|---|---|
| fact | ∞ | 无 | 是 | 用户显式否定 | 不衰减 |
| preference | 90 天 | 无 | 是 | 新偏好覆盖旧偏好 | 降权，不删除 |
| judgment | 180 天 | 有（可空） | 是 | 新判断（保留演化链） | 降权，保留供回溯 |
| commitment | 到期日 + 30 天 | 必须有 | 是 | 完成 / 取消 | 过期后降权并提示 |
| relation | 365 天 | 无 | 建议有 | 关系变更事件 | 降权 |
| event | ∞ | 无 | 是 | 不可覆盖 | 仅归档，不衰减 |

> 衰减只影响**自动注入的权重**，不影响可见性与可查询性。这是 00 里「衰减不删除」的落地。

### 1.5 输入编码协议（v6 增补）

手机与电脑上的显式输入（语音、文字、文件、分享），不直接成为记忆，必须先过**显著性闸门**：

```
salience = novelty × relevance × stake × consent × (1 - privacy_risk)
```

| 因子 | 计算 | 缺省 |
|---|---|---|
| novelty | 1 − 与近 30 天情景的最大相似度 | 相似度 >0.92 视为重复 |
| relevance | 与当前项目/目标/活跃话题的相关度 | 无上下文时取 0.5 |
| stake | 命中承诺、金额、时间、人名、决定 | 命中任一取 1.0 |
| consent | 录制前是否已明确告知且不在禁区 | **未知即 0** |
| privacy_risk | 是否可能含他人敏感信息 | 检测到即上调 |

四档输出：

| 档位 | 条件 | 行为 |
|---|---|---|
| 丢弃 | salience < 0.2 或 consent = 0 | 仅留在 10 分钟环形缓冲，不落盘 |
| 缓冲 | 0.2 ≤ salience < 0.4 | 暂存 24 小时，未再被提及即删 |
| 编码 | 0.4 ≤ salience < 0.7 | 写入 `episodes` + `episode_segments` + 事件 |
| 待确认 | salience ≥ 0.7 或含承诺 | 编码并进入候选确认队列 |

编码规则：

- 一个语音片段 → 一个 `episode_segment`；相邻片段按 5 分钟窗口聚为一个 `episode`。
- `privacy` 继承来源标签；含 `local_only` 的片段不得进入出网请求（06 §2）。
- 默认**不保存原始音频**；用户显式开启后最多保留 7 天，且可按时间范围一键清除（I11）。
- 说话人只保留匿名标签 A/B，不做身份识别（I13）。
- 去重：同一说话人、相似度 >0.92、72 小时内，合并为一条并累加引用。

失败关闭：`consent` 未知、麦克风权限缺失、录制被用户停止、或隐私扫描未完成时，一律不编码。

## 2. 修正与版本协议

### 2.1 修正流程

修正**不是 UPDATE**，而是「关闭旧版本 + 插入新版本」：

```
1. 校验：目标存在且 status='active'，tx_to IS NULL
2. 旧行：tx_to = now
3. 新行：version+1，supersedes_id = 旧行 id，
         tx_from = now，valid_from = 用户指定的生效时间（默认 now），
         origin = 'user_confirmed'，fidelity = 'pass'
4. 写确认事件 events(kind='correction', actor='user')
5. 重算引用：memory_refs 中指向旧行的记录迁移到新行
6. 标记受影响摘要：`conversation_memories.tainted = 1`
```

**历史不可删**：旧行永远保留，用于「三个月前系统眼中的你」。这是 A4 与 A5 的共同要求。

### 2.2 传播规则

当一条记忆被修正或遗忘时，所有引用它的对象按如下处理：

| 引用方 | 修正后 | 遗忘后 |
|---|---|---|
| 会话摘要 | 置 `tainted=1`，**不参与注入**，但档案可见并注明「所引判断已更新」 | 级联删除该摘要中的相关引用；摘要本身保留（它记录的是当时发生的事） |
| 用户偏好常量 | 重算：无引用则删除该维度 | 删除该维度 |
| 张力记录 | 若冲突已消解 → `auto_resolved` | 级联删除 |
| 图谱边 | 权重重算 | 删除边 |
| 注入历史 | **不修改**（历史就是历史） | 保持，但展示时标注「该记忆已遗忘」 |

> 关键判断：**注入历史是审计记录，不能因为记忆变了就篡改过去**。否则「为什么它当时那么说」就永远查不清。

### 2.3 撤销修正

修正本身也可撤销：再次修正回原内容会生成新版本，而不是删除中间版本。版本链是单向的、只增的。

## 3. 冲突仲裁协议

### 3.1 五条规则（优先级从高到低，写死）

| # | 规则 | 例 |
|---|---|---|
| R1 | 用户显式否定 > 一切 | 用户说「我不再这么想」→ 旧判断立即 `superseded` |
| R2 | 用户确认 > 系统推断 | 系统推断「你偏好简洁」，用户修正为「要详细」→ 采纳用户 |
| R3 | 同一 `valid_time` 区间、同一 `subject+predicate`，后写入者取代前者 | 同一天两次改主意，以最后一次为准 |
| R4 | **不同** `valid_time` 区间 → 不是冲突，是演化 | 9 月选 B、11 月选 A，两者都对，用于回溯 |
| R5 | 无法判定 → 生成张力，显式呈现，不静默择一 | 两句话语义对立但主题略有偏差 |

**禁止**：用「新 > 旧」覆盖跨时间的认知变化（违反 R4 会让「过去的你」永久失真）。

### 3.2 张力检测管线

```
新记忆 active
   │
   ├─ 1. 候选召回：同 subject/predicate（若有）+ 向量 top-20，sim ≥ 0.72
   │
   ├─ 2. 区间判定：valid_time 是否重叠
   │        └─ 不重叠 → 判定为「演化」，结束（不产生张力）
   │
   ├─ 3. 对立判定：NLI/LLM 二分类，输出 contradiction ∈ [0,1]
   │        └─ < 0.6 → 结束
   │
   ├─ 4. 计分：tension = sim × contradiction × recency × stake
   │
   ├─ 5. 去重：pair_hash = hash(min_id, max_id) 已存在 → 跳过
   │
   └─ 6. 入库 tensions(state='open')，等待质询预算
```

### 3.3 计分与阈值

```
tension = clamp(sim, 0, 1)
        × contradiction
        × exp(-|Δdays| / 180)
        × stake

stake: judgment=1.0, commitment=0.9, relation=0.7, preference=0.5, fact=0.3
θ 初始 = 0.55；命中条件 tension > θ
```

### 3.4 质询预算与自适应

| 约束 | 值 | 实现 |
|---|---|---|
| 单场对话 | ≤1 | `probes` 按 `session_id` 计数 |
| 全天 | ≤3 | `probe_budget` 按本地日期原子自增 |
| 静默时段 | 默认 23:00–08:00 | `settings.quiet_hours` |
| 捕捉模式 | 永不质询 | 入口判断 |
| 同一对记忆 | 30 天内不重复 | `tensions.surfaced_at` |
| 反馈 | 相关 / 不相关 / 已处理 | `probes.feedback` |

自适应：

```
最近 20 次质询的 irrelevant_rate > 50%
  → θ += 0.05（上限 0.80）
连续 3 次 relevant
  → θ -= 0.03（下限 0.40）
「已处理」→ 直接关闭对应 tension
```

### 3.5 呈现规范

质询必须包含四项，缺一不可：

```
你 9 月 12 日的对话里说过：
「方案 B 更适合长期维护」（来源：会话 2026-09-12，原文可展开）
这与你现在说的「方案 A 更稳妥」不一致。
—— 相关 / 不相关 / 已处理
```

禁止措辞：「我记得你……」「你总是……」「你一向……」——任何不带日期与原文的断言都违反 A4。

## 4. 注入协议

### 4.1 分层与配额

| 层 | 内容 | 配额 | 更新时机 |
|---|---|---|---|
| L1 | 原子事实、承诺、高置信判断（用户已确认） | ≤500 tokens，常驻 | 写入即更新 |
| L2 | 按当前话题检索的摘要/判断 top-3 | ≤300 tokens | 每轮实时 |
| L3 | 偏好常量（压缩后） | ≤100 tokens | 季度重估 |

总预算 ≤900 tokens。**超预算时按层裁剪，永远先砍 L2、再砍 L1 的低分项，L3 不砍**。

Token 估算：优先用与模型一致的 tokenizer；不可用时按 `ceil(utf8_bytes / 3)` 估算，并在回执中标记 `estimated=true`。

### 4.2 候选生成

| 层 | 候选来源 | 数量 |
|---|---|---|
| L1 | `v_memory_current WHERE layer='L1'` 全量 | 全部 |
| L2 | 向量 top-20 ∪ FTS top-10，按 `memory_id` 去重 | ≤30 |
| L3 | `v_memory_current WHERE layer='L3'` 压缩成常量 | 1–5 条 |

语境的获取：取当前用户输入 + 最近 2 轮 + 会话标题，拼接为查询串；不使用整场对话（避免漂移）。

### 4.3 过滤（fail-closed 清单）

按顺序执行，任一不通过即 `dropped` 并记录 `reason_code`：

| # | 检查 | 不通过原因码 | 用户可见 |
|---|---|---|---|
| F1 | 来自 `v_injectable`（记忆）或 `v_injectable_summary`（摘要） | `EVIDENCE_UNRESOLVED` / `FIDELITY_FAILED` / `TAINTED` | 不展示为「依据」 |
| F2 | `tx_to IS NULL`（当前版本） | `SUPERSEDED` | 不展示 |
| F3 | 未过期（commitment/judgment） | `EXPIRED` | 不展示 |
| F4 | 隐私允许当前出口 | `PRIVACY_BLOCKED` | 明示「含仅本地内容」 |
| F5 | 未被遗忘（tombstone） | `FORGOTTEN` | 不展示 |
| F6 | 引用的源事件未 shredded | `EVIDENCE_SHREDDED` | 提示证据已删除 |
| F7 | 不在当前会话已用过的重复集 | `DUPLICATE` | 无感 |

> F1 的 `v_injectable` 已经把 I2/I4/I6 编码进 SQL。**注入代码不得绕过该视图**，这是代码评审的硬性检查项。

### 4.4 打分

```
score = 0.55 × semantic
      + 0.25 × importance
      + 0.10 × freshness
      + 0.10 × type_boost

semantic   = 余弦相似度（归一化到 0–1）
importance = confidence
freshness  = exp(-Δdays / halflife(type))，fact/event 恒为 1
type_boost = 承诺临近截止 +0.1；用户显式要求记住 +0.1；其余 0
```

### 4.5 预算裁剪

按层独立执行：

1. 依 `score` 降序贪心选取。
2. 每加入一条，计算与已选集合的最大相似度；`MMR = 0.7×score - 0.3×max_sim`，低于阈值则跳过（去冗余）。
3. 累计 token 超过该层配额即停止。
4. 记录每条 `rank / tokens / score / decision`。

**确定性要求**：同一输入、同一记忆集合、同一配置，必须产生同一注入集。所有随机性（如抽签）禁止出现在注入路径。

### 4.6 冲突注入

命中 F1–F7 后仍有未仲裁冲突（`tensions.state='open'`）时：

- **两条都注入**，各带 `conflict_flag=1` 和对方 id。
- 提示词中显式说明「以下两条判断存在冲突，回答时需指出并请用户澄清，不得自行择一」。
- 占用两条的 token 配额；若超预算，先注入两条的**摘要式压缩版**，不丢弃其中一条。

### 4.7 注入回执

每轮生成后写入两处：

**逐条明细**（`injection_log`）：turn_id、memory_id、layer、rank、tokens、score、decision、reason_code、evidence_ok、conflict_flag。

**轮次汇总**（`receipts.kind='injection'`）：

```json
{
  "turn_id": "01J...",
  "session_id": "01J...",
  "injected": [
    {"memory_id": "01J...", "layer": "L1", "tokens": 63,
     "evidence": {"type": "turn", "id": "01J...", "quote": "记住：导师要求11月交初稿"}}
  ],
  "dropped": [
    {"memory_id": "01J...", "reason_code": "FIDELITY_FAILED"}
  ],
  "conflicts": ["01J...", "01J..."],
  "budget": {"L1": 412, "L2": 188, "L3": 40, "estimated": false},
  "created_at": 1790000000000
}
```

**UI 契约**：回答下方「依据」展开后展示 `injected` 与 `dropped`。用户能回答两个问题：「它为什么这么说」和「它为什么没提那件事」。

### 4.8 可重放

回执存储了 score 与 rank，因此审计时**不需要重算**。重放规则：

- 按 `turn_id` 查 `injection_log`，按 `rank` 还原注入顺序。
- 若记忆已修正/遗忘，仍展示当时的 `quote` 与 `memory_id`，并标注「该记忆后来已更新/已遗忘」。
- 禁止用当前状态覆盖历史回执。

### 4.9 世界知识与用户知识分注（v0.4）

| 类型 | 来源 | 标注 | 预算 |
|---|---|---|---|
| 世界知识 | `documents` / `chunks` / `facts` | 「文档 · 第 X 页」 | 与 L2 共享 |
| 用户知识 | `memory_entries` | 「你说过 · 日期」 | L1/L2/L3 |

规则：

- 两类分开检索、分开打分、分开裁剪；不得把文档片段伪装成「你说过」。
- 世界知识必须带 `document_id` + `chunk_id` + 定位区间；用户知识必须带 `memory_id` + `evidence_id`。
- 同分时优先用户知识（与当前任务更相关），但世界知识不得因预算被完全挤掉：至少保留 1 条。
- 冲突时先呈现用户知识，再给世界知识的反例，不静默选边。

### 4.10 检索计划与注入的契约（v0.4）

- 检索产候选，注入只消费**带可解析证据**的候选；两段之间以 `retrieval_run_id` 衔接。
- 一次回答必须同时有 `retrieval_run` 与 `injection_log`；缺一视为审计缺陷。
- 世界知识与用户知识在检索阶段就分开路由，在注入阶段分开标注，不得合并成一条「记忆」。
- 检索弃权时，注入层不得用模型常识补洞；回答应明确「没有找到依据」。
- 用户修正后，下一次同类检索必须优先取修正后的版本（新鲜度校验）。

## 5. 保真度协议

### 5.1 三级校验

| 级别 | 时机 | 方法 | 结果 |
|---|---|---|---|
| 自动对齐 | 写入时 | evidence 的 `quote` 必须能在源文本中定位（span 匹配）；断言为原文子串或改写度 ≤ 阈值 | `pass` / `pending` |
| 自动交叉 | 写入后 | 同一会话内多次出现的判断与摘要比对，冲突则降级 | `minor_deviation` |
| 人工抽检 | 每周 | 随机 10 条 + 全部 `confidence < 0.6` + 被注入 ≥3 次的高频条目 | `pass` / `minor_deviation` / `severe_distortion` |

> 自动对齐让绝大多数 `user_explicit` 条目无需人工即可 `pass`，人工抽检只处理真正模糊的部分。没有这一步，`v_injectable` 会让系统无记忆可用。

### 5.2 判定与四类严重歪曲

| 类型 | 定义 | 例 |
|---|---|---|
| `not_said` | 系统声称用户说过，但原文没有 | 「你说过要辞职」——原话是「考虑过」 |
| `polarity` | 否定说成肯定，或反之 | 「你不喜欢 X」记成「你喜欢 X」 |
| `misattribution` | 他人/系统的观点记为用户 | 把助手的建议记成用户的判断 |
| `fabricated_detail` | 编造具体数字、日期、承诺 | 「你答应周三交付」——原文无日期 |

判定为 `severe_distortion` 时，同时记录 `distortion_kind`（04 §5.4）。

### 5.3 冻结与回滚

```
单条严重歪曲
  → 该条 status='corrected'，fidelity='severe_distortion'，禁止注入
  → 写 correction 事件
同类问题累计 2 次（同一 generator）
  → settings.frozen_generators += generator（model@prompt_hash）
  → 摘要任务切换上一版本 generator
  → 重跑最近 7 天的摘要，产物置为 fidelity='pending'
```

**不冻结整个系统**。粒度为生成器版本，可定位、可回滚、可对比（对应 00 §6.2）。

### 5.4 与注入的关系

- `pass` / `not_applicable` → 可注入。
- `pending` → **不注入**，但档案可见并标「待复核」。
- `minor_deviation` → 不注入；修正后重新进入。
- `severe_distortion` → 不注入，且触发上节流程。

## 6. 遗忘协议

### 6.1 预览（不写任何数据）

`POST /v1/forget/preview` 返回：

```json
{
  "target": {"type": "memory", "id": "01J...", "preview": "导师要求11月交初稿"},
  "impact": {
    "memory_versions": 3,
    "refs": {"summary": 2, "injection": 14, "preference": 1, "tension": 1, "edge": 4},
    "derived_summaries": 2,
    "devices_pending_ack": ["phone-01"],
    "backup_retention_until": 1792592000000
  },
  "options": {
    "also_delete_source_event": false,
    "also_delete_session": false
  },
  "confirm_token": "01J..."      // 10 分钟内有效，一次性
}
```

### 6.2 七步级联

| 步 | 动作 | 失败处理 |
|---|---|---|
| 1 | `memory_entries` 所有版本 → `status='forgotten'`，`content=NULL` | 事务内重试 3 次；失败即整体回滚，不半删 |
| 2 | 按 `memory_refs` 清理引用：偏好维度、张力、边、候选 | 逐类记录成功数 |
| 3 | 向量：删除 `vec_memory` 中对应行；`fts_memory` 同步删除 | 失败则标记 `needs_reindex` |
| 4 | 图谱：删除 `edges` 两张相关边 | 记录条数 |
| 5 | 物化视图 / 缓存失效重建 | 重建失败不影响结果 |
| 6 | 写 `tombstones`（id + content_hash + forget_job_id） | 唯一约束冲突视为已完成 |
| 7 | 下发 `forget` 事件，等待其他设备 ack（超时 7 天则全局隐藏） | 超时仍保持 `awaiting_ack` |

若 `also_delete_source_event=true`：额外销毁该事件的 `crypto_keys`、置 `event_payloads.cipher=NULL`、`payload_state='shredded'`，并将其派生记忆一并级联。

### 6.3 墓碑与防复活

- `projector` 在创建任何记忆前，先按 `content_hash` 查 `tombstones`；命中则跳过。
- 事件重放时若 `payload_state='shredded'`，无法产生内容，自然不复活。
- 墓碑本身永久保留（仅 id 与哈希，不含内容），这是「证明删过」的唯一凭据。

### 6.4 跨端

- `forget` 事件随同步通道下发；各端执行本地级联后回 `sync_acks`。
- 未 ack 的设备：该条在**所有端**由 `v_injectable` 与列表查询双重过滤，界面标「删除中」。
- 回执中如实列出未确认设备名。

### 6.5 备份

- 每日快照保留 7 份，默认保留期 30 天。
- 遗忘**不会**立即重写历史备份。
- 回执必须写明：「备份中的副本将在 YYYY-MM-DD 前后自然过期；在此之前无法从备份中单独抹除。」
- **禁止**在回执中写「已彻底删除」而实际备份仍在。

### 6.6 回执

`receipts.kind='forget'`：

```json
{
  "forget_job_id": "01J...",
  "target": {"type": "memory", "id": "01J..."},
  "steps": [
    {"step": 1, "name": "memory_entries", "ok": true, "affected": 3},
    {"step": 2, "name": "refs", "ok": true, "affected": 18},
    {"step": 3, "name": "vectors", "ok": true, "affected": 3},
    {"step": 4, "name": "edges", "ok": true, "affected": 4},
    {"step": 5, "name": "projections", "ok": true},
    {"step": 6, "name": "tombstone", "ok": true},
    {"step": 7, "name": "devices", "ok": false, "pending": ["phone-01"]}
  ],
  "backup_retention_until": 1792592000000,
  "state": "awaiting_ack",
  "created_at": 1790000000000
}
```

**没有回执的遗忘视为未完成**（I6）。

### 6.7 部分遗忘与整场删除

| 操作 | 影响 | 用于 |
|---|---|---|
| 遗忘单条记忆 | 该条 + 引用；源事件保留 | 记错了一条 |
| 遗忘单条事件 | 事件内容粉碎 + 全部派生记忆 | 「这句话不要留」 |
| 删除整场会话 | 会话内全部事件粉碎 + 全部派生记忆 + 摘要 | 「这场对话从没发生过」 |

三种操作共用同一套七步流程，区别只在 `target_type` 与级联范围。

### 6.8 遗忘的边界（必须诚实告知）

系统**无法**删除：

- 已发送给云端模型的请求（供应商侧的策略由其决定）。
- 用户自行复制/导出的内容。
- 数据库目录之外的系统级备份。

这些必须在 `06` 与首次使用引导中明确写出，并在回执页面提供同样的说明。**隐瞒边界比遗忘不彻底更致命**。

## 6A. 认知巩固协议（v6 增补）

巩固是记忆从「情景」沉淀为「语义」的过程，与遗忘互补：遗忘是删，巩固是化。

### 6A.1 触发

| 触发 | 条件 |
|---|---|
| 夜间 | 本地时间 02:00–05:00，设备充电且空闲 |
| 手动 | 设置页「立即巩固」 |
| 补偿 | 连续 48 小时未成功巩固时，下次空闲补跑 |

### 6A.2 步骤（可中断、可续跑）

1. **重放**：读取窗口内 `episodes` / `episode_segments` / 事件。
2. **去重**：合并同一事实的多次表达，保留最强证据。
3. **抽象**：情景 → 语义（「每周三晚开会」→ `world_facts`）。
4. **实体消解**：同名人物/项目合并；不确定时保留两条并标注。
5. **更新世界模型**：新增、失效、修订；全部先写 `proposed`。
6. **张力复检**：新事实与既有判断对立 → 生成张力，进入质询预算。
7. **剪枝**：低显著性、无引用、超期的情景降权或归档（不删除）。
8. **重嵌入**：摘要与语义记忆重建索引。
9. **生成报告**：`consolidation_runs.changes_json` + 晨报（可选）。

### 6A.3 约束

- 巩固产出的推断一律 `proposed`，不得直接 `active`（I12）。
- 每次巩固必须写 `consolidation_runs`，记录窗口、统计、变更清单。
- 巩固必须具备幂等性：同一窗口重复执行结果一致。
- 预算上限固定；超预算时优先完成「张力复检」，其余顺延。
- 用户可对一次巩固执行「撤销」：回滚其产生的 `world_facts` 与摘要，但不影响原始事件。
- 失败时保留中间状态并标 `failed`，下次从断点继续；已有记忆不受影响。

### 6A.4 与遗忘的边界

- 巩固不删除记忆，只降权、归档、抽象。
- 遗忘优先于巩固：已 `forgotten` 的内容不得被重新抽象出来（墓碑校验）。
- 若巩固试图复活已遗忘内容，视为缺陷，记为 I12 违规。

## 6B. 整理协议（知识库写入）

> 记忆协议管「关于你的判断」，整理协议管「世界知识的组织」。两者共用事件、证据、回执与撤销。

### 6B.1 动作清单

| 动作 | 说明 | 改源文件 |
|---|---|---|
| 打标 | 给文档/分块加主题、类型、项目标签 | 否 |
| 归类 | 放入集合/视图 | 否 |
| 去重 | 标记重复或近似重复，建议保留主副本 | 否 |
| 合并 | 归一同一实体的多个写法 | 否 |
| 关联 | 建立文档—文档、文档—实体、实体—实体边 | 否 |
| 摘要 | 生成文档/集合摘要 | 否 |
| 补全元数据 | 推断标题、作者、日期 | 否 |
| 归档 | 在知识库中降权/隐藏 | 否 |

**永不改名、移动、删除源文件（I14）。**

### 6B.2 五步闭环

```
建议 propose → 预览 preview → 确认 confirm → 执行 apply → 回执 receipt
                                      ↑                    │
                                      └──── 撤销 undo ─────┘
```

| 步骤 | 要求 |
|---|---|
| 建议 | 带动作、对象、理由、置信度；批量生成 |
| 预览 | 展示影响范围、条目数、能否撤销 |
| 确认 | 低风险可批量；合并实体、标记重复必须逐条 |
| 执行 | 只改知识库；接受去重会写 `duplicate_of`，默认从检索隐藏；写事件 + 回执；失败整批回滚 |
| 撤销 | 30 天内可一键回滚；撤销写补偿事件 |

### 6B.3 自主度

- 默认**建议 + 人确认**，不自动执行任何写操作。
- 低风险：打标、归类可批量确认。
- 高风险：合并实体、标记重复、归档必须逐条预览。
- 未来放开自动化，须先在 10 定义误操作率与回滚闸门。

### 6B.4 质量要求

| 项 | 要求 |
|---|---|
| 理由 | 必须可读，例如「路径含齿科且与 3 篇文献主题相似」 |
| 可撤销 | 执行后 30 天内可回滚 |
| 冲突 | 两个分类冲突时呈现，不静默选一个 |
| 不臆造 | 元数据缺失就留空，不猜 |
| 可审计 | 每次执行可反查建议、确认人与影响条目 |

### 6B.5 失败处理

- 批次中单条失败：只回滚该条，其余继续；回执标注部分成功。
- 知识库写入失败：源数据不受影响，重试即可。
- 撤销失败：保持原状并告警，不显示「已撤销」。

## 6C. 问答沉淀协议（P1，ADR-0009）

> 整理协议（6B）管"世界知识的组织"，沉淀协议管"问答结果如何成为可复用的 Wiki 条目"。两者共用建议 + 人确认 + 撤销骨架，区别于 6B 的是：沉淀的产物是 wiki 页，不是对文档/实体的标注。

### 6C.1 六阶段流水线

```
问题捕获（保留原始提问 + 改写版本 + 标准版本）
  → 答案生成（走正常检索，不做特殊逻辑）
  → 沉淀判定（保守，宁漏勿滥）
  → 格式化（JSON Schema 输出：标题/摘要/正文/相关实体/来源引用/标签）
  → 人确认（单键确认；拒绝填原因，回流为负样本）
  → 双写入库（wiki_pages 关系库 + wiki 向量检索库）
```

### 6C.2 沉淀判定（保守优先）

满足 **≥2 条** 才进入格式化：

| # | 信号 | 判定 |
|---|---|---|
| 1 | 含具体事实 | 配置参数、接口名、数值、日期、操作步骤 |
| 2 | 有复用价值 | 其他问题很可能命中同类主题 |
| 3 | 30 秒可给出结论 | 摘要对读者直接可用 |

判定 Prompt 必须让 LLM 同时输出 `title_suggestion` 与 `summary`——生成标题会强制再做一次提炼（外部实践：单纯 true/false 准确率约 75%，加标题摘要后约 88%）。输出必须是 JSON Schema，不用自由文本。

**禁止**：生产环境自动入库（I18）。无论判定多高置信，都必须经人确认。

### 6C.3 节流与去重

| 约束 | 值 | 实现 |
|---|---|---|
| 单日沉淀上限 | 10 条 | `compile_runs` 按天计数 |
| 相似问题 | 已存在相似 wiki 页 → 转"更新建议"而非新建 | 向量相似 ≥0.92，同一 embedding（I19） |
| 重复来源 | 同一 `source_refs` 已沉淀 → 跳过 | `source_refs` 归一化哈希 |
| 确认率过低 | <60% 连续 4 周 → 阈值上调/暂停自动沉淀 | ADR-0009 复审条件 |

### 6C.4 撤改与版本

- 人确认后 30 天内可撤销：wiki 页转 `archived`，向量删除，写补偿事件。
- 人编辑 wiki 页：不直接覆盖，写 correction 事件 + 新版本行（`wiki_page_versions`），`supersedes_id` 指向旧版。
- 编译产物默认 `created_by='system'` + `status='proposed'`；人确认写 `updated_by='user'` 后才可 `active`（I18 触发器）。

### 6C.5 与记忆写入的边界

- 沉淀产物是**世界知识**（可复用结论），不是"关于用户"的记忆；不得进入 `memory_entries`，不受 L1/L2/L3 注入预算约束。
- 若沉淀内容涉及用户个人判断/偏好，走 05 §1 的记忆写入链，不走本节。
- 两类都要求 evidence：记忆的 evidence 指向 turn/event，wiki 页的 evidence 指向 source chunk（I16）。

## 7. 双时态查询协议

| 查询 | 语义 | 实现 |
|---|---|---|
| `current()` | 现在的认知 | `v_memory_current` |
| `as_of(T)` | T 时刻的认知 | `tx_from ≤ T AND (tx_to IS NULL OR tx_to > T)` 且 `valid_from ≤ T AND (valid_to IS NULL OR valid_to > T)` |
| `evolution(subject, predicate)` | 看法如何变化 | 同键多版本按 `valid_from` 排序，标注每次变化 |
| `history(memory_id)` | 某条的完整版本链 | 沿 `supersedes_id` 反向遍历 |

**禁止**：

- 用 `created_at` 代替 `tx_from` 做快照。
- 在 `as_of` 结果中混入 `status='forgotten'` 且内容已空的行（应展示为「该条已遗忘」）。
- 把 `as_of` 结果当作「用户当时的原话」——它只是「系统当时记下的判断」，原话在 evidence。

## 8. 运行时校验

每晚执行一次（`scripts/check-invariants`），结果写入本地日志并在设置页展示：

| 检查 | 对应不变量 | 失败动作 |
|---|---|---|
| `events` 是否有被修改的痕迹（哈希链） | I1 | 报警，停止写入，提示从备份恢复 |

| 是否存在注入行缺少 `memory_id` | I3 | 标记该轮回执不完整 |
| 是否有 `fidelity != pass` 的条目在 L2 | I4 | 立即从索引移除 |
| 是否有 `local_only` 出现在近期出网请求 | I5 | 触发审计报告 |
| 是否有 `forgotten` 仍出现在任何视图 | I6 | 强制重建投影 |

| 是否有 LLM 调用缺 `llm_tasks` 记录 | I9 | 报警（预算账本失真） |
| 是否存在 `system_inferred` 且 `active` | I10 | 降级为 `proposed` |
| 原始音频留存是否超 7 天 | I11 | 立即清除并记录 |
| 巩固产出是否有直接 `active` | I12 | 降级并标记该 run 失败 |
| 说话人是否出现可识别身份字段 | I13 | 删除字段并告警 |
| 是否存在写源文件的代码路径 | I14 | 阻断发布 |
| 整理动作是否绕过确认与回执 | I15 | 回滚并标记 |
